# Changelog

## 0.3.1 (unreleased)

**Upgrading from 0.3.0, read this first:**
- **Why:** 0.3.0 could report `passed` without testing what a file said (the paths are listed under Fixes, with rerunnable files in [the advisory](advisories/0.3.0-false-pass/README.md)), and had the injection paths listed under Security.
- **Pins:** `pip install netdryrun==0.3.0` still installs 0.3.0, and `uses: netdryrun/netdryrun@v0.3.0` keeps running 0.3.0 until you change it to `@v0.3.1`.
- **Run `netdryrun validate`.** Files that 0.3.0 accepted can now exit 2: quoted booleans, an unknown `afi` or `protocol`, duplicate keys, `min: 0` on its own, `vrf: all`, a `hold` with no effect, a misspelled top-level or `nodes` key, `afi: evpn` on EOS or SR Linux. Each of those was a check that didn't test what it said. Validate catches config problems only, so also rerun a representative lab.
- **Some verdicts change with no config edit:** received paths count as present even when not selected; SR Linux's own routes no longer fail `present: false`; best-path attribute checks wait for BGP convergence; `ping` with `expect: failure` passes when the destination is unreachable; a scenario session that the fault takes down indirectly (iBGP over a path behind the cut) needs a `bgp_session` check with `state: down`, or the scenario's negative checks fail as not evaluated.
- **Exit codes:** 0 passed, 1 checks failed, 2 not tested (config or lab problem, including "the fault did not take effect" and a report that couldn't be written), 3 inconclusive. A lab of the same name that is already running is refused and left alone. The Action deletes report files already in the workspace before it runs.

### Security

- **Names that reach a device command are checked.** `vrf` names are restricted to letters, digits and `. _ : -` (at most 64 characters), and `link_down` interface names to Linux interface names (at most 15 letters, digits and `. _ @ -`), before they go into `vtysh -c`, `sr_cli`, `Cli -c` or `ip link`. Before, a `netdryrun.yml` with a newline or a pipe in one of these names could run a second command inside a lab node. Configs that used other characters now fail validation (exit code `2`).
- **SR Linux:** the `attr-id` and the neighbor address read from device output are checked before they go back into a CLI command, so output from a lab node can't add to that command.
- **Markdown summary and PR comment are inert.** HTML, links, images, `@mentions` and `#123` references from configs or device output are escaped, and code blocks are sized so device output can't close them. Before, text from a lab could forge content in a PR comment or ping people.
- **`netdryrun record`:** warnings that quote device output stay on one YAML comment line, so device output can't add keys to the recorded baseline.
- **MCP server:** a new optional `NETDRYRUN_MCP_ROOT` confines the configs, the labs they point to, topologies and report reads to the listed folders (0.3.0 had no such setting and ignores the variable). `detail` and `error` in tool results are flattened to one line and capped (300 and 1,000 characters). The evidence file is never written through a planted symlink. `record_baseline`'s `wait_seconds` is bounded (0 to 600).
- **GitHub Action:** report files already in the workspace (committed in the PR, or left by an earlier run on a self-hosted runner) are deleted before the run, and the `status` output is `error` unless the report matches the run's own exit code, so a PR can't fake a pass with a committed report. The `inconclusive-reason` output is one line without quotes, backslashes, `$` or backticks.

Impact: in the Action, `netdryrun.yml` comes from the pull request, so on 0.3.0 a pull request could put a second command (through `vrf` or `link_down`) into a privileged lab container, or forge the PR comment. 0.3.1 allowlists those fields and escapes the comment. MCP stays able to reach labs outside the folders you meant until you set `NETDRYRUN_MCP_ROOT`; put it in your agent's MCP configuration.

### Fixes

- **`present: false` on SR Linux no longer fails on the router's own routes.** SR Linux lists its own static and interface routes in its BGP RIB as locally originated paths (neighbor `0.0.0.0`), whether or not an export policy advertises them; this was seen live on SR Linux 26.7.2. So on a router with a static default, `bgp_route` with `present: false` and `route` with `protocol: bgp, present: false` for `0.0.0.0/0` failed even when no peer sent a default. Those rows no longer count for `present: false`, and the `route` check no longer reports them as BGP routes. Best-path checks (`bgp_route` with attributes) still read them, so asserting `as_path: ""` on a router's own route works as before. Found while building the new `examples/srl-hidden-leak` lab.
- **The Markdown summary and PR comment of a big lab.** A GitHub comment holds at most 65,536 characters, and the summary listed every check (about 90 characters each), so above roughly 700 checks (a recorded 20-node lab gets there) the Action's `pr-comment` was rejected with a misleading permissions warning. The table now stops before the limit, failures first, and says how many checks it left out; the JSON and JUnit reports still have every check. Found by a 20-node scale test.

A pre-launch audit and a cold code review looked for ways a run could say `passed` without testing what the file says. The fixes below close the paths they found; the limits that remain are in [the advisory](advisories/0.3.0-false-pass/README.md#limits-that-remain-in-031). Some configs that 0.3.0 accepted are now refused (exit code `2`); each of those was a check that didn't test what it said. Run `netdryrun validate` after upgrading.

Fixes for runs that could pass without testing what they said:

- **A misspelled key outside a check no longer drops it silently.** 0.3.0 already refused unknown keys inside a check or a scenario, but ignored them at the top level (a misspelled `checks:` block, for example a list of leak guards under `chekcs:`, never ran), under `nodes.<node>` (a misspelled `driver` was ignored), and inside `node_isolated`. Unknown keys are now errors at every level, with a "did you mean" suggestion.
- **Quoted booleans no longer flip a check.** `present` and `active` must be unquoted `true` or `false`; `"false"`, `0`, `null` and empty values are errors. Before, `present: "false"` was read as true.
- **An unknown `afi` no longer reads as 0 prefixes.** `afi` must be `ipv4-unicast`, `ipv6-unicast` or `evpn`. Any other family counted 0 prefixes, which passes `max` and `exact: 0`.
- **An unknown `protocol` no longer matches nothing.** `protocol` must be one of the names the drivers report (the list is in the [reference](https://netdryrun.com/reference/config/#protocol-names)); `ebgp`, `ibgp`, `direct` and similar get a suggestion. Before, other names were passed through, matched no route, and silently passed `present: false`.
- **Duplicate YAML keys are errors**, in `netdryrun.yml` and in the topology. Plain YAML keeps the last one, so a second `checks:` block or a repeated `present:` silently replaced the first.
- **`min: 0` on its own is refused** (it always passes), and **`hold` on a check where it has no effect is an error** instead of being ignored.
- **`vrf: all` is refused.** Devices answer it keyed by each VRF's name, which the drivers read as "no routes".
- **`afi: evpn` on Arista EOS and SR Linux is refused before the lab deploys.** Those drivers read only the IPv4 and IPv6 unicast counts (SR Linux has no received-routes counter for EVPN, so the driver skipped the family), so an EVPN count always read 0 and passed `max` and `exact: 0`. FRR and SONiC read the EVPN count from the router's BGP summary; a family a neighbor doesn't carry counts as 0 received prefixes.
- **Scenario checks are never judged on the state from before the fault.** After taking links down, a scenario waits until the BGP sessions over those links are down on both ends (capped at the largest timeout of its checks), then settles; positive checks must pass on 2 consecutive samples and then hold for `--hold`. If the fault never shows, the run ends with exit code `2`, "the fault did not take effect". Before, a scenario's positive checks could pass on the network as it was before the failure.
- **Negative checks wait for every BGP session on their node.** A post-convergence check starts only once every configured BGP neighbor on its node is established with stable prefix counts (neighbors a `bgp_session` check expects down don't count), capped at its timeout. If a session never comes up, the check fails as "not evaluated" and names it. Before, a leak arriving over a session nobody checked could come after the check had already passed.
- **`bgp_route` attribute checks are judged after convergence.** A `bgp_route` that asserts any best-path attribute (`next_hop`, `as_path`, `as_path_regex`, `local_pref`, `med`, `communities`, `without_communities`) is now a post-convergence check: it waits for every BGP session on its node, the settle delay, and must hold for `--hold`. Before, all of these except `without_communities` passed on 2 early samples, so they could pass on a temporary best path that changed when a slower session came up. A `bgp_route` with no attributes (the best path exists) is still a positive check. `hold` is now accepted on these checks.
- **A node with no BGP neighbors at all is not converged.** The BGP gate released at once when a node reported no neighbors, the answer of a node whose BGP config isn't applied yet, so a leak that arrived later passed `present: false`. The gate now keeps waiting, up to its cap (the check's `timeout`). If the node still reports no neighbors then, its post-convergence checks run with a warning in their result that they were evaluated without BGP convergence; the verdict is unchanged. A node without BGP therefore adds one `timeout` of waiting to its post-convergence checks.
- **A scenario whose BGP state can't be read before the fault stops with exit code `2`.** Before taking links down, a scenario reads the BGP sessions on both ends of each link (and the downed interfaces' addresses) to know which sessions the fault must bring down. A read that failed counted as "no sessions", so the scenario skipped the wait for the fault to take effect and was judged after the settle and hold only. Now the run ends with a one-line error naming the node, before any link goes down. "No BGP session runs over the downed links" is logged only when the state was read and shows none (a node without a driver, or a VRF the node says it doesn't have, still counts as none).
- **Post-convergence checks in a scenario wait for the BGP gate.** Inside a scenario, a post-convergence check (a leak guard, a `max` prefix count) now waits, as at the top level, until every BGP session on its node is up with stable prefix counts, capped at its timeout. Sessions over the links the scenario took down don't count, nor do sessions a `bgp_session` check expects down. Before, these checks were judged right after the settle delay; for `inject_routes`, the run had only waited for the prefixes to be in the injecting node's own table, so a leak still on its way to the node under test could pass. A peer with a long advertisement interval can still delay the routes beyond the gate (documented); a session the fault takes down indirectly (iBGP over a downed path) needs a `bgp_session` check with `state: down` in the scenario, or the checks fail as "not evaluated".
- **Drivers never read an error as "nothing".** A VRF that doesn't exist is an error on every driver (FRR and SONiC confirm it with `show vrf`, SR Linux with the network-instance's oper-state, Arista EOS by its `vrfs` map), and so are a failed command and output the parser doesn't recognize (empty output, a wrong type, a renamed field). Before, some of these read as "no routes" or "no prefixes", which passes `present: false` and `max`. Arista EOS no longer ignores a failed `show ipv6 bgp summary`, and SR Linux no longer ignores a failed neighbor local-preference lookup.
- **Received paths count as present on every driver**, valid or not, selected or not: SR Linux no longer skips invalid paths, and FRR's `route` check now also reads the BGP table. The router's own paths (network statements, redistribution) don't count as received.

Other fixes:

- **Number ranges.** `timeout` and `hold` must be positive and at most 86400 seconds; ping `count` 1 to 1000; `min_replies` 1 to `count`, and not with `expect: failure`. Before, `count: 0` and `min_replies: 0` were accepted, the top-level `timeout` was not checked, and `.inf` passed as a timeout.
- **`ping` with `expect: failure` passes when the destination is unreachable.** With no route at all, ping prints "Network unreachable", "No route to host" or "Destination unreachable" and sends nothing; that was reported as "ping did not run" and failed.
- **SIGTERM and SIGHUP clean up like Ctrl-C.** The lab is destroyed (unless `--keep`), a `--json` report with `status: error` is written, and the exit code is 128 plus the signal: 143 for SIGTERM, 129 for SIGHUP, 130 for SIGINT. A second signal can't interrupt the cleanup. The MCP server destroys the labs it is running when it gets SIGTERM.
- **Crashes and bad input exit 2 with one line**, never a traceback or exit code `1` ("checks failed"): bad YAML (with its line and column), wrong types, bad topologies, a negative `--settle` or `--hold`, and internal errors. `--debug` or `NETDRYRUN_DEBUG=1` prints the traceback. With `--json`, an error report is written, including for a config error.
- **A report that can't be written after the verdict exits 2 with a clear line.** If `--json`, `--markdown`, `--junit` or the step summary can't be written (an unwritable path, a missing folder), every other report is still written, and each failure prints `could not write <path>: <reason>; the verdict was <status>`. The exit code is `2`: the evidence asked for is missing. Before, the first failure was reported as an internal error and the remaining reports were not written.
- **A lab with the same name already running is refused** with exit code `2`, and left alone, instead of being redeployed and then destroyed. Two runs of the same lab started together on one host are refused by a lock. A run that never deployed never destroys anything: an error found before deploying (a typo in a node name) no longer destroys a lab you kept running with `--keep`.
- **`netdryrun validate` reads the topology** and makes the checks `run` makes before deploying, without Docker or containerlab: unknown nodes, nodes without a driver, keys a node's driver can't read, `inject_routes` on a non-FRR node, and link faults on SR Linux nodes. The MCP `validate` tool does the same. Before, `validate` said `OK` to a file that `run` then refused.
- **The Markdown summary and PR comment show the proof.** The evidence for a failed check lists every command of its final sample (a route check reads the routing table and the BGP table), and the excerpt keeps the lines that say which route the device selected, with their protocol. Before, the excerpt of a "not selected" leak stopped before the `selected` field.
- The MCP `check_types` tool lists `hold` among the keys every check accepts.
- **Releases carry signed build provenance** (Sigstore, SLSA): verify a downloaded wheel with `gh attestation verify <file> -R netdryrun/netdryrun`; the bundle is also attached to each GitHub release.
- **Install instructions use `pipx install netdryrun`** (or `uv tool install netdryrun`). Ubuntu 24.04 and Debian 12 refuse a plain `pip install` outside a virtualenv, so the old first command failed there.

### Added

- **New example `examples/srl-hidden-leak`** ("The route leak ping can't see"): SR Linux and FRR each receive a leaked default route that loses to their own static, so sessions, ping and the routing table all look fine. The README shows how to see it by hand on each NOS; the checks catch each leak with one `bgp_route` `present: false` guard.
- **Agent evaluation** (`examples/agent-eval/`): ten pre-registered tickets on the example labs, each with a hidden grader, worked by fresh headless Claude Code agents that had only `AGENTS.md`, the AI agents page and the MCP tools. Results, misses included: [RESULTS.md](examples/agent-eval/RESULTS.md).
- **JSON Schema for the report**: `website/docs/schemas/report-v1.json`, published at https://netdryrun.com/schemas/report-v1.json (draft 2020-12). Tests validate reports from real lab runs against it.
- **MCP: Windows paths work when the server runs in WSL.** With Claude Code on Windows and `netdryrun mcp` in WSL (the documented Windows setup), the tools now accept `C:\...` as well as `/mnt/c/...`, so an agent can pass the one path its file tools use. In the agent evaluation, Claude Haiku 4.5 used the WSL path with its Windows file tools and was refused on every ticket; that path mismatch caused 5 of its 7 failures (T06 and T09 failed for other reasons).
- `AGENTS.md`: for a change that must not change behavior, record a baseline first (a `passed` covers only the checks that exist); on Windows, which path to pass.
- **MCP: `"unready": true` on a failed check that never got usable state** from its node (the command failed, or BGP had no neighbors at all). The inconclusive rule is conservative, so a lab with `bgpd` off on every router still comes back `failed` when other nodes' route and ping checks read cleanly; the flag and `AGENTS.md` now help an agent tell that from a bad change. Found by the agent evaluation's broken-lab ticket.
- **`inject_routes` failure fault** (FRR nodes): a scenario makes a node announce extra routes (`prefixes`, or `count` consecutive ones from `from`, optional `as_path` prepend), then removes them. Use it to test that a max-prefix limit or an import filter holds when a customer or peer misbehaves. Prefixes the node already has configured, and non-FRR nodes, are refused before anything changes.
- **Verdict Corpus v2** (`corpus/v2/`, `python corpus/run.py --corpus v2`): its own base lab, intent spec and 18 pre-registered cases that re-express the v1 misses (unexpected routes, latent risks, rigid prefix counts, a vendor-default label) and add new changes. v1 results are unchanged.
- New `Published release` workflow: the released Action by its tag on `frr-bgp` (must pass) and `frr-bgp-broken` (must fail), and every documented install line from PyPI (`pip install`, `uvx netdryrun`, an MCP handshake over `uvx netdryrun mcp`) on Python 3.10 to 3.15. Runs on pushes to `main` and weekly.
- Python 3.11 and 3.14 are listed in the package classifiers. The published-release workflow installs and runs Netdryrun from PyPI on 3.10 to 3.15; CI runs the unit tests on 3.10, 3.12 and 3.13, and the release gate runs them on 3.10 to 3.14 and in a plain container.
- The source distribution no longer includes the website's demo video and its copies of the demo GIFs.

## 0.3.0 (2026-10-27)

- **Friendlier long waits:** the deploy line says it usually takes 30-90 s (longer when images are pulled), and Ctrl+C prints "Interrupted: no verdict" with exit code 130 instead of a Python traceback. The lab is still cleaned up. Found on the first real Codespaces run.
- **New check type `bgp_route`: attributes of the BGP best path.** `communities` (must carry all; standard, large and well-known names), `without_communities` (must carry none), `as_path` (exact) and `as_path_regex`, `local_pref`, `med` and `next_hop`, plus `present: false` (no path at all in the BGP table). Many real policy bugs are attribute-level: a route that is still there but lost its community, got the wrong local preference, or now goes the long way. Works on FRR, SR Linux, Arista EOS and SONiC; every parser is tested against output captured from live labs, and the examples gained `bgp_route` checks. A key a driver can't read stops the run before deploying with "not supported on `<driver>`" (today every driver reads every key). `netdryrun record --attributes` (and `record_baseline(attributes=true)`) also pins each BGP route's AS path, local preference and communities.
- **New status `inconclusive` (exit code `3`)**: checks failed, but the lab never reached a testable state, so the run says nothing about the change. The rules are conservative: nothing passed on any sample anywhere in the run, and every failing node never returned usable BGP state (its CLI never answered, or BGP had no neighbors at all). A configured session that is down is always `failed`, because an ASN typo looks the same as a slow lab. The JSON report gains `inconclusive_reason` and `"unready": true` on such samples; the Markdown summary and PR comment say so; JUnit reports those checks as errors, not failures; the MCP verdict is `INCONCLUSIVE: the lab did not reach a testable state; this says nothing about your change. Do not apply it until a run passes.`; the GitHub Action reports `status: inconclusive` and a new `inconclusive-reason` output, and still fails the job. Rules: [CLI and reports](https://netdryrun.com/reference/cli/#when-a-run-is-inconclusive).
- **Report schema `netdryrun.report/v1` stays v1**: this release only adds things (the `inconclusive` status value and the `inconclusive_reason` field, plus `unready` in history samples). A consumer that only knows `passed`, `failed` and `error` should treat any other status as not passed.
- A `bgp_session` or `bgp_prefixes` check on a node with no BGP neighbors at all now says so ("no BGP neighbors at all on this node") instead of "seen: none".
- **`netdryrun feedback`** opens a short GitHub feedback form, prefilled with only the version and platform; nothing is sent until you submit it. After an interactive run (not in CI), one line points to it. New **design partners** page: free help testing one real change, in exchange for feedback.
- **Try it in your browser:** a devcontainer (`.devcontainer/`, containerlab's Docker-in-Docker image with containerlab 0.81.1, Netdryrun installed from the checkout, FRR image pre-pulled) and an "Open in GitHub Codespaces" badge, so the agent demo runs with nothing installed.
- **Agent demo** (`examples/agent-demo`): a ticket, a tempting change that passes the ticket checks but leaks routes (rejected), and the proper fix (accepted). `demo.sh` replays it and checks that attempt 1 fails only on the leak guards; CI runs it on pushes to `main` and on pull requests.
- MCP server reports its version and website in `serverInfo`.

## 0.2.0 (2026-10-27)

- **Fix: a change that breaks a baseline check no longer turns a scenario run into `error`.** The recovery check after a scenario now only requires the checks that passed before it; a network that really doesn't recover is reported as failed `[after <scenario>] recovers: ...` checks (exit 1), not a lab error (exit 2). Found by running the edge-guard pack against the Verdict Corpus.
- **SONiC driver** (docker-sonic-vs): sessions, prefix counts, routes, ping, record, failure scenarios. New `nodes.<node>.setup` key runs post-boot configuration commands (retried until the NOS is ready). New example: `examples/sonic-frr`.
- **Arista EOS driver** (cEOS-lab, bring your own image): sessions, prefix counts, routes (routing table + BGP table), ping, record, failure scenarios. New example: `examples/arista-frr`.
- **Leak detection fixed on SR Linux and Arista**: a leaked BGP route that is received but not installed (it lost to a static or local route) only appears in the BGP table on those platforms. Both drivers now read it, so `present: false` fails as it should. Found by live leak tests; regression tests use real captured output.
- **`netdryrun record`**: snapshot a known-good running lab into a `netdryrun.yml` baseline (BGP sessions, exact prefix counts, BGP routes), so you don't write checks by hand.
- **Failure scenarios**: `scenarios:` with `link_down` and `node_isolated` faults. Links are always restored, and the network settles before the next scenario.
- **Faster runs**: positive checks are polled together against one shared convergence window, and post-convergence checks hold together. A badly broken change now costs about one timeout instead of one per failing check (the corpus runs 2-3x faster).
- **GitHub Action `pr-comment: true`**: one pull-request comment with the verdict and the evidence for each failed check, updated in place on every push.
- **PR-ready evidence**: the Markdown summary now includes the exact command and the relevant raw output for each failed check.
- **`state: down`** for `bgp_session`: any state except established.
- **`active: false`** for present routes: accept a route that is in the table but not selected.
- **MCP built in**: `netdryrun mcp` starts the server (no extra install). New `record_baseline` tool. Listed in the official MCP Registry metadata (`server.json`).
- **Network Change Verdict Corpus**: 30 pre-registered cases comparing ping-only, session-only and Netdryrun checks, with losses published.
